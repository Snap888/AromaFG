# AromaFG repository audit — 2026-11-09

## Scope and evidence

This audit used the repository-analysis rubric supplied for AromaFG, the full-repository and code-generation requirements, the repository README, the current PR/branch graph, the Phase 3.3 CI artifact metadata, and targeted source review.

No physical Android device was connected during this audit. No Adreno, Turnip, Qualcomm proprietary-driver, Winlator borrowed-device, or real-game run is claimed. The audit did not modify the optical-flow algorithm, Vulkan runtime implementation, or public C API.

### High — Phase 3.1 smoke-test ordering in PR #12

The initial PR #12 device smoke source called `aroma_fg_process(engine, &input, &output)` before `input` and `output` were declared and before `AromaFGVulkanFrameV2` had been initialized. The cancel/retry test was reordered in commit `b8bd6c1aae726d0abe0a37139d784169e0bd37a3`: the host payload is now initialized before the first recording attempt, the command pool is reset before cancel, and the same frame ID is retried after re-recording host image initialization.

**Validation status:** no workflow run or commit status was available for that PR head at audit time. The fix is not CI-verified.

### High — ADB target ambiguity and device compatibility

The Phase 3.3 ADB runner previously used bare `adb` commands. It now:
- requires exactly one authorized device or an explicit serial (argument 3 / `ADB_SERIAL`);
- scopes device commands through `adb -s SERIAL`;
- checks arm64-v8a availability and Android API 26+ before pushing binaries;
- records the selected serial and ABI/API in the report.

The documentation now describes explicit target selection.

### High — Termux artifact provenance

Added `tools/run-aromafg-termux.sh`. It pins the previously successful Android arm64 artifact, checks GitHub artifact metadata (run ID, source SHA, digest, expiry), verifies the ZIP SHA-256 and embedded commit, syntax-checks the downloaded runner, and falls back to the Termux home directory if shared Downloads is unavailable or unwritable.

The pinned artifact is run `42527383441`, artifact `13635768192`, source commit `5d1daabee160fffda4a8ffee1c78140003454899`, SHA-256 `32e3d1a2aed099687e1e09a7c047a089ef005a69ef49d762802d7a5e4118db42`. These pins must be updated together when a newer artifact is used.

### CI changes

The Phase 3.3 workflow now includes Bash syntax checks and ShellCheck at error severity for both Android helper scripts. The new commits have not yet produced a check result visible to this audit. The previously successful run #42527383441 validates the earlier Android cross-build and Linux lavapipe path only; it does not validate the new scripts or a physical device.

### High — flow resolution control and mobile memory budget

The public `AromaFGConfig.flow_scale_percent` currently scales flow-vector magnitude in the synthesis shader; it does not change the flow-image resolution. The runtime allocates full-resolution level-0 forward/backward flow and refined flow/confidence images. This differs from the low-resolution flow optimization called for by the Adreno notes and can be misread by integrators as a performance-resolution control. The public header and backend/flow documentation now state the actual semantics; configurable low-resolution flow remains unimplemented.

For 1920×1080, the current seven-level pyramid contains about 2.765 million total pyramid pixels. Counting the allocated luma, forward/backward flow, confidence and seed images across the pyramid plus full-resolution refined flow/confidence gives approximately 91.2 MB (about 87 MiB) of private image payload, before source/output images, allocation overhead and driver bookkeeping. This is a sizing estimate from current allocation dimensions/formats, not a measured heap report. The payload scales roughly with pixel count; 4K would be several hundred MiB. Phase 5/6 now includes reducing intermediate memory and adding measured multi-resolution profiling.

The physical smoke used 320×180 and measured about 5.322 ms flow/refine, 0.210 ms preprocessing and 0.205 ms synthesis. These values validate execution only; they are not representative full-resolution performance evidence.
